# 抽奖活动回归用例分类与执行边界 v1

## 文档说明

- 适用范围：WEEX 转盘抽奖活动后管回归、前端回归、专项回归。
- 目标：把现有用例重新梳理成可自动执行的 4 类，明确哪些必须新建活动、哪些必须串行承接、哪些必须建专项活动、哪些可以复用已有活动。
- 适用对象：测试设计、自动化编排、dispatcher / resolver / manifest 维护。

## 审计结论

当前用例库和编排稿已经完成了 `状态污染识别`，但还没有把 `执行分类` 彻底落成自动化硬规则。

当前主要缺口有 3 个：

1. `Fresh 要求` 只表达了“要不要新建活动”，没有表达“是否是新建活动的起点 case”。
2. 一部分 case 需要承接前一步状态，但文档里只写了 `依赖`，没有升格为执行器必须遵守的硬约束。
3. 一部分 case 属于专项活动，但当前口径仍容易被误塞进普通主回归。

## 四类权威分类

### A类：一次性状态校验，必须新建活动

定义：

- 该 case 的目标状态只能在 fresh 活动里出现一次。
- 不能使用已报名、已发 MQ、已抽奖的旧活动复跑。
- 这类 case 是某条链路的起点 case。

机器口径：

- `executionClass = FRESH_ROOT`

### B类：串行链路校验，可在同一活动内依次执行

定义：

- 这类 case 本身不要求“每条都新建活动”。
- 但必须承接同一条链路中的上一步状态。
- 脱离上一步单独执行会导致误判或 `SKIPPED`。

机器口径：

- `executionClass = CHAIN_CONTINUE`

### C类：专项活动校验，必须单独建专项活动

定义：

- 这类 case 必须绑定专项模板或专项活动。
- 不能混入普通主回归活动。
- 专项活动之间也不应互相复用。

机器口径：

- `executionClass = SPECIAL_ACTIVITY`

### D类：只读 / 结构校验，可复用已有活动或已有数据

定义：

- 不依赖一次性状态。
- 不改变关键业务状态，或改变后不影响后续主链路判定。
- 可以使用稳定在线活动、稳定后管数据重复执行。

机器口径：

- `executionClass = REUSABLE_READONLY`

## FE-81 / FE-82 / FE-84 的机器可执行口径

| Case ID | executionClass | activityPolicy | accountPolicy | requiredState | nextState |
| --- | --- | --- | --- | --- | --- |
| FE-81 | `FRESH_ROOT` | `CREATE_NEW_NORMAL_ACTIVITY_STARTED` | `UNREGISTERED_ACCOUNT` | 活动进行中、账号未报名 | 仍为未报名可见 `立即报名` |
| FE-82 | `CHAIN_CONTINUE` | `REUSE_PREVIOUS_ACTIVITY` | `REUSE_PREVIOUS_ACCOUNT` | 承接 FE-81 | 账号变为已报名，按钮切到 `抽奖` |
| FE-84 | `CHAIN_CONTINUE` | `REUSE_PREVIOUS_ACTIVITY` | `REUSE_PREVIOUS_ACCOUNT` | 承接 FE-82 / FE-21，已报名、次数为 0、充值任务未完成 | 发 MQ 后次数 > 0 或任务态更新 |

说明：

1. `FE-81` 不能复用已经报名过的旧活动。
2. `FE-82` 不应脱离 `FE-81` 单独执行。
3. `FE-84` 可以和 `FE-81 / FE-82` 使用同一条 fresh 活动，但不能复用已发过 MQ 的旧活动。

## 作为执行器硬规则的建议

后续 resolver / dispatcher 不应再只判断 `Fresh 要求`，而应改为判断：

1. `executionClass`
2. `activityPolicy`
3. `accountPolicy`
4. `requiredState`
5. `nextState`

只要这 5 个字段落到机器可读层，执行器就能真正避免 case 状态污染。
