# 转盘抽奖自动化回归落地方案

## 文档说明

- 适用范围：WEEX 转盘抽奖活动的后管自动化回归、前端自动化回归、专项自动化回归。
- 当前目标：把已沉淀的后管 56 条、前端 84 条回归用例，拆成可持续执行的自动化主回归与专项回归。
- 当前原则：先落稳定主链路，再补专项；不把高波动、低复现、强并发场景直接塞进日常全量回归。

## 关联文档

- 后管回归用例集：`docs/test-cases/lottery-admin-regression-cases.md`
- 前端回归用例集：`docs/test-cases/lottery-frontend-regression-cases.md`
- 编排设计稿：`docs/workflows/lottery-regression-orchestration-design.md`
- 机器可读 manifest：`docs/workflows/lottery-regression-manifest.json`

## 一、自动化目标

本方案希望解决 4 件事：

1. 让转盘抽奖的后管和前端回归可以按固定链路重复执行。
2. 让活动、账号、任务、库存等测试数据不互相污染。
3. 让自动化执行不仅能“跑动作”，还能判断结果是否正常。
4. 让专项场景和日常主回归分层，避免一次回归依赖过多复杂前置条件。

## 二、自动化范围分层

### A. 稳定主回归

适合日常执行，优先自动化：

- 后管：
  - 活动列表
  - 报名模版
  - 任务管理
  - 奖品管理
  - 活动配置 / 活动信息
  - 上下线 / 状态流转
- 前端：
  - 页面基础 UI
  - 抽奖样式 UI
  - 页面状态 UI
  - 按钮与交互态
  - 单抽主流程
  - 我的奖品 / 奖励记录
  - 前后端联动展示

### B. 专项回归

适合按需执行，单独活动隔离：

- 五连抽专项
- 二次权重专项
- 小库存 / 无库存专项

### C. 暂不纳入当前自动化主回归

- 多账户并发抢奖

当前用户已明确：并发问题先不用管，当前按单账户自动化回归执行。

## 三、测试数据与活动隔离策略

### 1. 活动隔离

每次回归使用新活动，不复用旧活动。

活动至少拆成 3 类：

- `普通回归活动`
- `二次权重专项活动`
- `小库存专项活动`

活动获取方式支持两种：

- 新建活动
- 从活动列表复制活动后再修改

当前已确认：

- 活动复制 bug 已修复，可以作为自动化活动准备路径的一部分。
- 在 `活动列表 / 转盘抽奖` 页面，操作栏包含 `查看 / 修改 / 下线 / 复制` 等按钮。
- 点击 `复制` 后，会生成一个新的草稿状态活动。
- 活动前端访问 URL 规则为 `https://stg-www.weex.tech/zh-CN/events/draw/<活动别名>`。

### 2. 专项活动用途

`普通回归活动`：
- 用于后管主链路
- 用于前端页面展示
- 用于前端单抽主流程

`二次权重专项活动`：
- 仅用于验证累计次数再权重场景
- 不与普通活动共用

`小库存专项活动`：
- 用于库存不足 / 奖品被抢光场景
- 可以专门建成无库存或低库存活动

### 3. 账号策略

固定使用单账户执行前端自动化回归：

- 账号：`abc229@qq.com`
- 密码：运行时读取，不写入仓库文档

用途：
- 报名参加活动
- 完成任务获取抽奖次数
- 执行前端抽奖链路回归

注意：
- 账号信息只能保存在 skill 本地 `.env.local` 或运行时输入中
- 不允许写入 docs、skills、脚本参数、git 历史
- 自动化执行前应先验证该固定账号当前凭证可登录；若 `login/new` 返回账号密码错误，则本轮应先停止并更新有效凭证，再继续执行前端回归。

## 四、前置流程标准化

前端自动化回归不应直接从“打开活动页点击抽奖”开始，而应先完成前置链路。

标准前置流程：

1. 创建或复制本轮目标活动。
2. 根据回归类型，配置活动：
   - 普通活动
   - 二次权重活动
   - 小库存活动
3. 绑定报名模版。
4. 绑定抽奖任务。
5. 配置奖池。
6. 上线活动。
7. 使用固定测试账号登录前端。
8. 报名参加活动。
9. 完成前置任务，获取抽奖次数。
10. 打开活动前端页，执行对应前端用例。

## 五、活动页入口与报名规则

当前已真实验证的稳定规则：

1. 转盘抽奖活动前端页必须通过活动别名访问：
   - `https://stg-www.weex.tech/zh-CN/events/draw/<活动别名>`
2. 活动必须先在后管完成 `上线`，再进入前端验证。
3. 活动未开始时，前端主按钮应展示 `即将开始`。
4. 活动进行中且当前用户未报名时，前端主按钮应展示 `立即报名`。
5. 点击 `立即报名` 后，`apply` 接口成功返回时，主按钮应从 `立即报名` 切换为 `抽奖`。
6. 已报名账号再次进入同一活动页时，不应再次展示 `立即报名`，应直接展示 `抽奖`。

报名能力的最小自动化闭环应包含：

1. 登录固定测试账号。
2. 打开活动别名 URL。
3. 判断当前按钮状态：
   - `即将开始`
   - `立即报名`
   - `抽奖`
4. 若为 `立即报名`，执行点击报名。
5. 断言报名成功：
   - `apply` 接口返回成功
   - 页面主按钮切换为 `抽奖`
6. 再次打开同一活动页，断言报名状态保持。

## 六、抽奖次数前置发放规则

当前已确认：前端回归前，需要先完成这些任务以获取抽奖次数：

- `合约交易量任务`
- `充值任务`

因此自动化回归要补一个固定前置能力：

- 先完成任务
- 再验证抽奖次数到账
- 次数到账后再进入前端抽奖

抽奖次数前置校验建议：

1. 活动页剩余抽奖次数显示正确。
2. 可用次数满足本轮测试要求：
   - 单抽：至少 `1`
   - 五连抽：至少 `5`

当前已真实验证的充值任务辅助链路：

1. 用户先登录并完成活动报名。
2. 发送充值 MQ 回调，当前已验证 Kafka UI topic 为：
   - `flink.exchange.spot_capital_order_info`
3. 当前已验证 payload 关键字段：
   - `user_id = <uid>`
   - `amount = <充值金额>`
   - `coin_id = 2`
   - `biz_type = 1`
   - `biz_sub_type = 1`
   - `status = 9`
4. MQ 发送成功的验证信号：
   - Kafka produce API 返回 `HTTP 200`
   - 页面出现 `Message successfully sent`
   - 消息列表可回查本次 `messageId`
5. 发送成功后，返回活动页刷新并回查：
   - `taskCompletions`
   - `raffle/frequency`
   - 或页面可用抽奖次数
6. 只有当活动页任务完成态或抽奖次数更新时，才算充值任务真正生效；仅 MQ 写入成功不等于活动任务已完成。

## 七、前端结果校验标准

### 1. 单抽

单抽自动化断言至少包含：

- 点击抽奖后成功发起请求
- 奖品弹窗展示正常
- 剩余次数减少 `1`
- 延迟 `5秒` 后，`我的奖品 -> 奖励记录` 中可查到新增结果
- 奖励记录字段正确：
  - `活动名称`
  - `奖励金额`
  - `获奖时间`
  - `备注`

### 2. 五连抽

五连抽自动化断言至少包含：

- 五连抽按钮展示条件正确
- 点击后成功发起请求
- 奖品结果弹窗展示正常
- 剩余次数减少 `5`
- 延迟 `5秒` 后，`我的奖品 -> 奖励记录` 中可查到新增结果
- 当前已确认：五连抽场景下，奖励记录按**多条记录**校验

### 3. 我的奖品 / 奖励记录

当前已确认命名口径：

- 页面入口名：`我的奖品`
- 点击后弹窗名：`奖励记录`

自动化断言至少包含：

- 点击入口可打开弹窗
- 奖励记录列表可展示数据
- 筛选交互可用
- 中奖弹窗与奖励记录结果一致

## 八、奖励记录时延处理

当前已确认：抽奖完成后，延迟 `5秒` 再检查 `我的奖品 -> 奖励记录`。

自动化建议：

- 先固定等待 `5秒`
- 再进入奖励记录断言

如果后续稳定性不够，再升级为：

- `5秒固定等待 + 轮询重试`

## 九、二次权重专项执行规则

当前已确认规则：

- 如果配置 `累计抽奖次数 N = 2`
- 且配置 `必中奖品 = 5`
- 则用户第 `3` 次抽奖命中奖品 `5`

即按 `N+1` 次开始生效。

自动化要求：

- 二次权重 case 必须使用专项活动执行
- 不要求验证二次权重的 case，不强制配置二次权重

推荐专项断言：

1. 第 `1`、`2` 次抽奖按普通配置执行。
2. 第 `3` 次抽奖命中指定奖品。
3. 奖励记录结果与二次权重配置一致。

## 十、小库存专项执行规则

当前已确认：

- 可以专门建一个活动，用于库存不足测试
- 该活动专门用于验证库存不足，不与普通回归活动共用

自动化目标：

- 验证库存不足时的前端反馈
- 当前先按“出现库存不足提示弹窗”断言

注意：

- 小库存活动不可复用为普通抽奖活动
- 跑完后活动状态已污染，下一轮应重新创建或复制新活动

## 十一、后管与前端自动化分工

### 后管自动化负责

- 模版、任务、奖品、活动配置创建和校验
- 活动上线 / 下线 / 删除 / 复制
- 奖池、任务、日历、多语言、FAQ 等配置回显
- 字符长度限制、字段显隐、保存成功校验

### 前端自动化负责

- 页面基础 UI 与样式展示
- 单抽 / 五连抽
- 按钮显隐与禁用态
- 奖品弹窗
- 我的奖品 / 奖励记录
- 前后端联动展示
- 库存不足提示、失败提示、异常恢复

## 十一、自动化执行顺序

### 主回归建议顺序

1. 后管依赖模块：
   - 报名模版
   - 任务管理
   - 奖品管理
2. 后管活动：
   - 活动列表
   - 活动配置 / 活动信息
   - 上下线 / 状态流转
3. 前端活动页：
   - 页面基础 UI
   - 单抽主流程
   - 我的奖品 / 奖励记录
4. 专项回归：
   - 五连抽专项
   - 二次权重专项
   - 小库存专项

## 十二、建议的自动化执行入口

后续建议在 skills 中最终形成 3 类入口：

### 1. 主回归入口

用途：
- 跑普通回归活动
- 覆盖稳定主链路

### 2. 二次权重专项入口

用途：
- 创建或复制专项活动
- 配置二次权重
- 执行 N+1 生效校验

### 3. 小库存专项入口

用途：
- 创建或复制小库存活动
- 执行库存不足提示校验

## 十三、当前不作为阻塞的问题

这些点当前已被用户确认，不阻塞自动化落地：

- 风控失败问题已解决，固定账号可用于报名与抽奖回归
- 并发问题当前不纳入主回归
- 概率统计当前只做二次权重专项，不做普通概率大样本统计
- 库存异常可通过独立小库存活动解决

## 十四、后续需要补充到 skills 的能力

为了真正让回归“自动跑起来”，后续 skills 需要补以下能力：

1. 新活动创建 / 复制后的标准化配置能力
2. 普通活动、二次权重活动、小库存活动三类活动模板能力
3. 固定账号登录和报名能力
4. 前置任务完成并领取抽奖次数的能力
5. 前端抽奖动作与奖励记录断言能力
6. 主回归与专项回归的入口编排能力
